# PR #18 follow-up review — F1/F3 (2026-11-20)

## Scope

This follow-up is limited to the read-only Wine prefix discovery path in PR #18.
It does not change Registry persistence, same-UID race handling, Bottle creation,
or the CAT compatibility claims.

## F1 — Wine registry header parsing

The parser now validates the actual Wine Registry v2 preamble rather than
searching the file for an isolated matching line:

- the first line must be exactly `WINE REGISTRY Version 2` (LF or CRLF);
- at most one exact `#arch=win32` / `#arch=win64` option is accepted;
- the option must occur before the first registry key section;
- malformed, duplicate (including identical duplicates), and conflicting
  declarations remain UNPROVEN;
- a matching string after the first key is registry content, not header proof;
- short reads, the 4096-byte bound, and the sentinel-byte truncation rule remain
  in force; if the first key is not reached within the bounded window and EOF
  is not known, uniqueness cannot be established and architecture stays UNPROVEN.

The layout is grounded in Wine's own writer/parser: Wine emits the v2 banner
and architecture option in the preamble, and its loader treats unknown or
mismatched architecture options as invalid. See
https://github.com/wine-mirror/wine/blob/master/server/registry.c
and the Wine registry writer's `save_all_subkeys` implementation.

Added negative regression tests cover a forged banner, an architecture line
after the first key, duplicate identical declarations, conflicting declarations,
and malformed declarations. Boundary coverage also proves that a valid-looking
architecture is not accepted when an oversized preamble may continue beyond
the read window with a second conflicting declaration. A positive test confirms
that an architecture declaration after the first key does not invalidate the
single valid preamble declaration.

## F3 — bounded scan semantics

The scan retains at most 4096 entries from the directory iterator and processes at most 64 directories.
The retained sample is sorted before processing. This makes processing order stable within the collected sample, but **does not make sample membership independent of filesystem `readdir` order when more than 4096 entries exist**.

When either cap is exceeded, the code emits `PARTIALLY_PROVEN` evidence. Consumers must not interpret a capped scan as a complete inventory. A globally deterministic selection would require examining the full directory (or a different indexed selection design), which is outside this bounded follow-up.
