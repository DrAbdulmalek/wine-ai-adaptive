# مواصفة الجناح النظيف المستوحاة من CrossOver — wine-ai-adaptive

**معرّف الوثيقة:** WAA-CCRS-001
**الإصدار:** 1.0.0-adapted.1
**الحالة:** معتمدة كتصميم مرجعي (المصدر كان DRAFT — Architecture Review Required)
**المشروع:** wine-ai-adaptive
**لغة التنفيذ:** Python (المكتبة القياسية فقط)
**المنصة الأساسية:** Linux / Manjaro KDE
**الـBackend الأساسي:** Wine
**ـBackend ثانوي اختياري:** CrossOver (محوّل مستقبلي — ليس شرطًا)
**ذكاء اصطناعي:** Ollama محلي (جرد فقط)
**المعمارية:** وحدوية، محايدة تجاه الـBackend، محلية أولًا

## 0) مصدر الوثيقة ونطاق التكييف

هذه الوثيقة نسخة **مكيَّفة على المستودع** من مسودة مواصفة وُلّدت في جلسة
خارجية (ChatGPT، رابطان بمشاركة المستخدم، 2026-11-11) بعنوان
«CROSSOVER_CLEAN_ROOM_SPEC.md – v1.0». وهي تتبع المنهجية المعتمدة في
`docs/AGENT_POLICY.md` و`docs/reviews/EXTERNAL_REVIEWS.md` (القسم 6):
**دمج ذكي لا نسخ حرفي** — كل بند من المصدر إما أُقتبس، أو أُعيدت صياغته
ليطابق قواعد المستودع، أو حُجز بسبب موثق.

### 0.1 ما تكيّف عن المصدر ولماذا

| المصدر (كما ورد) | التكييف في هذه الوثيقة | السبب |
|---|---|---|
| «JSON أو YAML» لصيغة الوصفات | JSON فقط | YAML يتطلب محللًا خارجيًا؛ مخالف لسياسة «المكتبة القياسية فقط» |
| بنية مستهدفة تُنشئ مجلدات جديدة (`installation/`, `recipes/`, …) | تُنشأ الوحدات عند تنفيذ مرحلتها فقط | المصدر نفسه نصّ على «بنية مستهدفة وليست أمرًا بإنشاء جميع المجلدات فورًا» |
| اختبارات الوصفات والتثبيت بأدوات خارجية محتملة | كل اختبار عبر `unittest` من المكتبة القياسية | قرار موثق في AGENT_POLICY (جولة التدقيق الثانية) |
| تصنيفات توافق مختصرة (PLATINUM/GOLD/…) | تبقى خارج نطاق الأدلة؛ المرجع هو النتائج التفصيلية وحالات الدليل الخمس | المصدر نصّ على أن التصنيف المختصر «عرض مستقبلي وليس مصدرًا للأدلة»؛ وحالات الدليل المعتمدة هنا هي `evidence.py` الخمس |
| أقسام المصدر الختامية بعد §13.2 (نموذج التهديد، خطة الاختبارات، المراحل) | أُعيدت صياغتها من سياسات المستودع نفسها (THREAT_MODEL / AGENT_POLICY / سير الاختبارات الفعلي) | نص المصدر المشترك لم يُستلَم كاملًا (قيود جلب المحتوى)؛ فأُنيبت هذه الأقسام لوثائق المستودع القائمة بدل تخمين ما لم يُرَ |

### 0.2 المبدأ الجوهري من المصدر (منقول نصًا بمعناه)

> نستطيع تفكيك الوظائف والسلوكيات المعلنة في CrossOver، ثم تصميم تنفيذ
> مستقل لها اعتمادًا على Wine والتوثيق العام والاختبارات. لا ننسخ
> الشيفرة الاحتكارية أو الوصفات الداخلية أو قواعد البيانات الخاصة أو
> نتجاوز ترخيص CrossOver.
>
> هذا هو المقصود بـ Clean Room: استنساخ الوظائف والسلوك، لا استنساخ
> التنفيذ البرمجي.

ثلاثة مبادئ حاكمة من المصدر، وهي متسقة مع هذا المستودع:

1. **Wine-first:** لا حاجة إلى CrossOver لتشغيل أي شيء في المشروع.
2. **Backend-neutral:** يمكن إضافة CrossOver أو KVM لاحقًا دون إعادة
   كتابة بقية النظام.
3. **Evidence-driven:** لا يُعلن توافق تطبيق إلا باختبارات موثقة
   لإصداره وبيئته المحددين.

## 1) الملخص التنفيذي

بناء منصة مفتوحة المصدر لإدارة تطبيقات Windows على Linux، مستوحاة
**وظيفيًا** من تجربة CrossOver دون نسخ شيفرتها أو مكوناتها الاحتكارية،
مع تفوق مقصود في: التخصص (تطبيقات CAT الطبية والترجموية: SDL Trados
Studio وmemoQ أولًا)، الشفافية، الأدلة المصنفة، والتحكم المحلي.

**قيد المستودع الحاكم فوق كل ما يلي:** كود التشغيل بالمكتبة القياسية
فقط بلا أي استثناء، offline-first، fail-closed في المسارات الحساسة،
لا root، لا كتابة إلى GitHub من كود التشغيل، وترخيص MIT — وفق
`docs/AGENT_POLICY.md`.

المبادئ الثمانية من المصدر (منقولة بمعناها):

| المبدأ | الوصف |
|---|---|
| Wine-first | Wine هو المحرك الأساسي |
| Clean-room | تنفيذ مستقل للوظائف، لا نسخ تنفيذ |
| Local-first | العمل محليًا دون خدمات سحابية |
| Evidence-driven | لا ادعاء توافق دون أدلة |
| Security-first | منع العمليات غير المصرح بها |
| Backend-neutral | فصل الإدارة عن محرك التشغيل |
| Reversible | كل تعديل مهم قابل للاستعادة |
| Human approval | لا تنفيذ حساس دون موافقة صريحة |

## 3) المعمارية المستهدفة

ست طبقات رئيسية (من المصدر، مع ملاحظات الالتزام):

```text
WINE AI ADAPTIVE
|
Application Interface            (Qt/KDE — مؤجلة، لا تستورد وحدات Wine مباشرة)
|
Application Services
|
+---------------+---------------+
|               |               |
Environment      Installation     Compatibility
Manager          Orchestrator       Engine
|               |               |
+---------------+---------------+
|
Backend Layer                    (Wine أساسي — CrossOver/KVM محولات اختيارية مستقبلية)
|
Linux Integration
|
Diagnostics / Security
|
Knowledge & Evidence
|
Local AI Assistant               (Ollama محلي — بلا صلاحية تنفيذ)
```

قواعد المعمارية (من المصدر §3.1، منقولة بمعناها — وهي أشد ما يكون

- لا تستورد طبقة الواجهة وحدات Wine مباشرة.
- لا تنفذ قاعدة المعرفة أوامر نظام.
- لا يملك مساعد الذكاء الاصطناعي صلاحية تنفيذ الأوامر.
- لا تتصل الوصفات بالنظام مباشرة.
- جميع العمليات الحساسة تمر عبر طبقة تنفيذ مركزية.
- نتائج التشخيص مستقلة عن واجهة المستخدم.

## 5) تجريد الـBackend (تصميم معتمد — لا تنفيذ بعد)

لا يجوز أن تعتمد بقية المنصة على أوامر Wine مباشرة. العقد الموحد
المستهدف (من المصدر §5):

```python
class ExecutionBackend:
    def detect(self): ...
    def get_version(self): ...
    def list_prefixes(self): ...
    def create_environment(self, config): ...
    def validate_environment(self, path): ...
    def launch_application(self, config): ...
    def collect_diagnostics(self, environment): ...
```

متطلبات كل Backend: اكتشاف الإصدار والقدرات، إدارة البيئات، تشغيل
التطبيقات، جمع السجلات، تقارير الأخطاء. **يجب أن يعلن Backend عن
الوظائف غير المدعومة بدل محاكاتها بصورة غير صحيحة.** محوّل CrossOver
اختياري مستقبلي ولا يشترط تثبيته.

ملاحظة التزام: أي تنفيذ لهذا العقد سيمر عبر `command.py`
(قائمة السماح للقراءة فقط) لكل عملية تشخيصية، وطبقة موافقة صريحة
لكل عملية كتابة — لن يُكتب أي تنفيذ قبل وجود نموذج تهديد واختبارات
لمعماريته (AGENT_POLICY: لا تحصين بلا اختبار).

## 6) Bottle Manager (إدارة بيئات Wine المستقلة)

### 6.1 الغرض

إدارة بيئات Windows المستقلة (Bottles/Prefixes): كل بادئة ليست آلة
افتراضية بل بيئة Wine مستقلة تحوي `drive_c` وسجل Windows وملفات
النظام والبرامج المثبتة وإعدادات Wine.

### 6.2 التخزين الافتراضي

```text
~/.local/share/wine-ai-adaptive/
├── prefixes/          # البادئات المُدارة (trados/ memoQ/ sandbox/…)
├── backups/
├── manifests/
├── logs/
└── metadata/
```

### 6.3 المسارات المحمية

`~/.wine` هو البادئة الافتراضية للمستخدم ويبقى **خارج** أي عمليات
تعديل أو نسخ تجريبي تلقائي — يكتشفه المشروع ويصنفه `protected`
ولا يكتب فيه أبدًا. كذلك أي بادئة يحددها المستخدم كبيئة محمية.
(ملاحظة: ذكر المصدر للمجلد `wine-cat-lab` حُوّل إلى
`wine-ai-adaptive` اتساقًا مع اسم المستودع.)

### 6.4 مصفوفة العمليات (من المصدر — المرجع التزامي)

| العملية | الأولوية | السياسة الأولية | الحالة |
|---|---|---|---|
| Discover | P0 | قراءة فقط | **منفَّذة** (`bottle_manager.discovery`) |
| Inspect | P0 | قراءة فقط | **منفَّذة** (`inspect_prefix`) |
| Inventory | P0 | قراءة فقط | **منفَّذة جزئيًا** (علامات البادئة والمعمارية والإصدار المعلن لاحقًا) |
| Validate | P0 | قراءة فقط | **منفَّذة جزئيًا** (فحص الوجود والروابط الرمزية؛ التحقق العميق لاحقًا) |
| Create | P1 | موافقة صريحة | محجوز |
| Clone | P1 | موافقة صريحة | محجوز |
| Backup | P1 | بعد فحص المساحة | محجوز |
| Restore | P2 | موافقة مستقلة | محجوز |
| Delete | P3 | **معطّل افتراضيًا** | محجوز — لن يُنفَّذ دون قرار مالك صريح |

### 6.5 المتطلبات الأمنية (من المصدر، مع تنفيذها الفعلي)

- رفض الروابط الرمزية غير المصرح بها — **منفَّذ**: مرشّح بادئة هو رابط
  رمزي يُرفض ولا يُتتبع (`lstat` + فحص `S_ISLNK`).
- التحقق من المسارات بعد canonicalization ومنع Path Traversal —
  **منفَّذ**: تطبيع المسارات دون تتبع الروابط (`abspath`) ورفض
  المرشح غير المجلد.
- منع الكتابة خارج جذر البيانات المصرح به — **بنيوي**: لا توجد أي
  عملية كتابة في طبقة الاكتشاف أصلًا.
- التحقق من المساحة الحرة — يخص عمليات Create/Backup المحجوزة.
- منع تعديل بادئة قيد الاستخدام — يخص العمليات الكتابية المحجوزة.
- تسجيل العمليات — كل نتيجة تحمل قائمة أدلة مصنفة.
- مراعاة TOCTOU — قراءة ترويسة `system.reg` عبر `os.open` بـ
  `O_NOFOLLOW` بحيث لا يُتبع رابط رمزي يُزرع بين الفحص والقراءة؛
  النافذة المتبقية موثقة في §14.

## 7) Installation Orchestrator (تصميم — محجوز)

لا ينفذ التثبيت مباشرة بمجرد العثور على ملف EXE. التدفق المستهدف من
المصدر: اكتشاف المثبت ← التحقق من الملف ← حساب SHA256 ← تحديد
التطبيق ← تحليل المتطلبات ← تخطيط البادئة ← تحليل التبعيات ← خطة
تثبيت ← **موافقة المستخدم** ← التنفيذ ← تحقق بعد التثبيت ← تسجيل
الأدلة.

التحقق من المثبت يسجل: اسم الملف، الحجم، SHA256، النوع، المعمارية إن
أمكن، المصدر إن عُرف، والتوقيع الرقمي إن كان قابلًا للتحقق — **ولا
يُعد وجود توقيع رقمي دليلًا كافيًا على سلامة الملف أو ملاءمته.**

## 8) Declarative Recipe Engine (تصميم — محجوز)

محرك وصفات مستقل وآمن لا ينسخ نظام CrossTie. الصيغة المستهدفة JSON
حصرًا (انظر §0.1)، بنفس حقول مثال المصدر (`schema_version`,
`application`, `prefix`, `requirements`, `dependencies`,
`installation`, `network`, `evidence.status = "UNVERIFIED"`).

قائمة العمليات المسموح بها داخل وصفة (مغلقة — الرفض الافتراضي لكل
ما عداه): `CreatePrefix`, `ValidatePrefix`,
`InstallApprovedDependency`, `RunApprovedInstaller`,
`SetWindowsVersion`, `ConfigureApprovedDLL`, `CreateLauncher`,
`CollectDiagnostics`. **لا أوامر حرة داخل الوصفات.**

أمن الوصفة: تحقق مخطط، تحقق تبعيات، قيود إصدارات، تحقق سلامة، إعلان
صلاحيات، سياسة شبكة (المعطل افتراضيًا)، خطة تنفيذ، استراتيجية تراجع.
أي وصفة مجهولة المصدر تبدأ بحالة `UNTRUSTED`.

## 9) Runtime Dependency Manager (تصميم — محجوز)

فئات التبعيات (من المصدر): .NET، Visual C++، الخطوط، DirectX، Gecko،
Mono، ODBC، مكتبات Windows DLL.

**حالات الدليل للتبعية (لا تُستخدم كلمة Installed وحدها)** — منقولة
كما هي لأنها تكمل سلم الأدلة في المشروع:

```text
NOT_DETECTED
DETECTED
VERSION_MATCHED
INSTALLATION_COMPLETED
FUNCTIONALLY_VERIFIED
FAILED
UNKNOWN
```

القاعدة المرجعية من المصدر: وجود Wine Mono لا يعني أن .NET Framework
4.8 مثبت أو متوافق، ولا يكفي أن يظهر المثبت ناجحًا — والتحقق الوظيفي
(FUNCTIONALLY_VERIFIED) هو ما يثبت اجتياز الاختبارات المطلوبة.

## 10) Compatibility Knowledge Base

### 10.1 العلاقة مع الموجود

`KnowledgeStore` (مخطط v3 بقيود CHECK كاملة + طبقة استعلام + تصدير
مجهّل) هي **أساس** هذه القاعدة. ما يضيفه هذا القسم تصميميًا: ربط كل
نتيجة توافق ببيئة الاختبار الفعلية كاملة (التطبيق وإصداره ورقم
البناء، إصدار Wine، معمارية البادئة، النظام والنواة والمكتبات، إصدار
.NET، خلفية الرسوميات، إعدادات البادئة، الاختبارات).

### 10.2 فئات اختبارات التوافق لتطبيقات CAT (من المصدر)

| الاختبار | الوصف |
|---|---|
| Installation | تثبيت التطبيق |
| Activation | التفعيل المشروع |
| Launch | التشغيل |
| UI | واجهة المستخدم |
| Fonts | عرض الخطوط |
| Project Creation / Reopen | إنشاء المشروع وإعادة فتحه |
| SDLXLIFF | فتح ملفات الترجمة |
| Translation Memory / Terminology | الذاكرة الترجموية والمصطلحات |
| Export | تصدير الملفات |
| Stability / Recovery | الاستقرار واستعادة جلسة العمل |

### 10.3 حالات التوافق

```text
UNTESTED / UNVERIFIED / PARTIALLY_VERIFIED / VERIFIED / REGRESSION / BROKEN / BLOCKED
```

لا يجوز إصدار حكم `VERIFIED` دون اختبارات موثقة. تصنيفات العرض
المختصرة (PLATINUM/GOLD/…) ليست مصدر أدلة ولا تُستخدم حتى تُعرَّف
معايير موضوعية لها.

## 11) Graphics Backend Manager (تصميم جزئي — الاكتشاف منفَّذ)

المكونات المستهدفة من المصدر: كشف GPU (منفَّذ في `probe.py`)، فحص
Vulkan (منفَّذ)، فاحص DXVK وفاحص WineD3D وملفات خلفيات وقياس
(مخططة). الخلفيات المستهدفة: WineD3D، DXVK، VKD3D-Proton عند
الحاجة المستقبلية.

**سياسة الاختيار (من المصدر):** لا يُختار DXVK تلقائيًا لمجرد توفره؛
يُوزن توافق التطبيق ودعم Vulkan وتعريفات GPU واستقرار الواجهة وعرض
النصوص واستهلاك الذاكرة ونتائج الاختبارات. **الأولوية لتطبيقات CAT
هي الاستقرار وصحة العرض، لا الأداء الرسومي الأقصى.**

---

## 12) Backup and Recovery (تصميم — محجوز)

متطلبات النسخ من المصدر: اكتشاف العمليات النشطة، التأكد من إغلاق
التطبيقات، جرد المحتويات، إنشاء Manifest، حساب SHA256، إنشاء أرشيف،
اختبار سلامة الأرشيف، تسجيل إصدار Wine وإعدادات البادئة. الأنواع:
FULL / INCREMENTAL / VERSIONED — **ولا يبدأ دعم Incremental قبل إثبات
صحة Full Backup والاستعادة بالاختبارات.**

سياسة الاستعادة: عملية مستقلة بموافقة جديدة؛ التحقق من الأرشيف
والمساحة والمسار والـManifest؛ إنشاء بيئة استعادة منفصلة وفحص الملفات
المستعادة قبل أي تبديل — **لا تستبدل الاستعادة بادئة قائمة مباشرة.**

---

## 13) Diagnostics Engine (الطبقات والفئات)

طبقات تحليل الفشل المستهدفة (من المصدر): التطبيق ← زمن تشغيله ←
إعدادات Wine ← البادئة ← الرسوميات ← مكتبات Linux ← النواة ←
العتاد.

الفئات: Missing DLL، فشل تهيئة .NET، Access Violation، فشل Vulkan،
فشل تهيئة الرسوميات، تلف البادئة، انهيار التطبيق، خطأ صلاحيات، مكتبة
Linux ناقصة.

الجزء المنفَّذ اليوم: استخراج وتصنيف رموز الأخطاء وتبارّي الأنماط
عبر `diagnostics/codes.py` + `log_parser.py` وأمر `diagnose` — بلا
نص خام ولا تخزين. تحديد «طبقة الفشل» هيكلًا شجريًا هو توسعة مستقبلية
تبني على هذه الأساسات.

### 13.1 تصنيف الأدلة (المستودع أصلًا)

```text
PROVEN / PARTIALLY_PROVEN / UNPROVEN / CONTRADICTED / BLOCKED
```

كل تشخيص يوضح: الملاحظة، مصدر الدليل، وحالة الإثبات — كما في
`evidence.py`.

## 14) نموذج التهديد للوحدات الجديدة

نموذج التهديد الأساسي للتخزين هو
[docs/THREAT_MODEL.md](THREAT_MODEL.md) (T1–T14). طبقة اكتشاف
البادئات الجديدة تُقيَّم ضد التهديدات القائمة كالآتي:

| التهديد القائم | المعالجة في طبقة الاكتشاف | الاختبار المثبت |
|---|---|---|
| T-فئة symlink (التتبع إلى مسار غير مقصود) | مرشّح بادئة رابط رمزي يُرفض؛ قراءة الترويسة بـ`O_NOFOLLOW` | `test_symlinked_prefix_candidate_is_rejected`, `test_reg_header_read_rejects_symlink` |
| T-فئة الملفات غير الاعتيادية (FIFO/جهاز) | فحص `S_ISDIR` على `lstat` قبل أي فحص آخر | `test_non_directory_candidate_is_skipped` |
| T-فئة البيانات الفاسدة | ترويسة سجل تُقرأ بحد 64 بايت وتُفسَّر بنمط صارم؛ ما لا يطابق يبقى UNPROVEN لا يُخمَّن | `test_unparsable_arch_header_stays_unproven` |
| خطر إفشاء مسارات عبر التصدير | طبقة الاكتشاف **لا تكتب في أي مخزن**؛ أي ربط مستقبلي بالتخزين يمر عبر `prefix_id` المجرد فقط | بنيوي (لا استدعاء تخزين في الوحدة) |

**الخطر المتبقي الموثق:** TOCTOU بين `lstat` والقراءة لا يُغلق كليًا
من فضاء المستخدم (نفس الصياغة الصادقة في THREAT_MODEL/README)؛
`O_NOFOLLOW` يضيّق النافذة عند قراءة الملفات. أي توسعة كتابية
(Create/Clone/Backup) **تُلزم بإدخالات تهديد جديدة واختبارات قبل
سطر كود أول** وفق AGENT_POLICY.

## 15) خطة الاختبارات ومعايير القبول

المشغّل: `unittest` من المكتبة القياسية حصرًا، محليًا وعبر CI
(3.11/3.12/3.13). كل الاختبارات على مجلدات مؤقتة (`TemporaryDirectory`)
— لا مساس ببادئات حقيقية أبدًا.

معايير قبول طبقة الاكتشاف P0 (مثبتة في `tests/unit/test_bottle_discovery.py`
و`test_cli.py`):

- بادئة سليمة win64/win32 تُكتشف وتُصنف معماريًا من ترويسة `system.reg`.
- مرشح بلا `drive_c` أو بدون ملفات السجل لا يُعد بادئة.
- الرابط الرمزي يُرفض ولا يُتتبع.
- `~/.wine` يُصنف `protected` دائمًا.
- `WINEPREFIX` المعلن بيئيًا يدخل كمرشّح صريح، وغيابه عن القرص يبقى
  UNPROVEN لا خطأ انهيار.
- تكرار نفس البادئة عبر جذور بحث متعددة يُدمج دون ازدواج.
- ترويسة غير قابلة للتفسير تبقي المعمارية UNPROVEN.
- تعارض الإشارات (ترويسة win32 مع وجود `syswow64`) يُسجل CONTRADICTED
  ولا يُحل بالتخمين.
- سقف المسح (عدد المجلدات لكل جذر) يمنع فحص أشجار ضخمة ويُسجل كدليل.
- أمر `wine-ai prefixes` يُخرج JSON صالحًا أو نصًا مقروءًا، ولا يخزن
  شيئًا ولا يفشل انهيارًا عند غياب كل البادئات.

## 16) خارطة الطريق P0–P11 (من المصدر، مُحاذاة للمستودع)

| المرحلة | المكوّن | النتيجة المطلوبة | الحالة |
|---|---|---|---|
| P0 | Architecture & Security Contract | عقد معماري وأمني | **منجزة** (هذه الوثيقة + LEGAL/THIRD-PARTY + THREAT_MODEL) |
| P1 | Bottle Discovery | اكتشاف Prefixes دون تعديل | **منجزة** (`bottle_manager.discovery` + CLI) |
| P2 | Bottle Manager | إدارة Prefixes مستقلة (بموافقة) | مخططة |
| P3 | Recipe Engine | وصفات تثبيت آمنة | مخططة |
| P4 | Runtime Manager | تشخيص التبعيات | مخططة |
| P5 | Compatibility Database | قاعدة أدلة التوافق | جزئية (أساس KnowledgeStore موجود) |
| P6 | Graphics Manager | إدارة DXVK/WineD3D | جزئية (اكتشاف فقط) |
| P7 | Backup & Recovery | نسخ واستعادة قابلة للتحقق | مخططة |
| P8 | Diagnostics Engine | تحليل الأعطال بطبقاته | جزئية |
| P9 | CAT Integration | Trados وmemoQ | مخططة |
| P10 | KDE GUI | واجهة رسومية متكاملة | مخططة (PySide6، والنواة تبقى مستقلة عن Qt) |

إلى التنفيذ دون مراجعة واختبارات وموافقة مستقلة — والعمليات الكتابية
(Create/Clone/Backup/Restore/Delete) لا تُنفَّذ دون طبقة موافقة صريحة
وسجل تدقيق، والحذف معطل افتراضيًا حتى بعد بناء الطبقة.
